Expose every model behind the same inference contract. The official NIM-on-Spark playbook is built around serving local completions over HTTP, and the local installation guide for Dynamo is explicitly centered on ending with a standard model-serving endpoint on Ubuntu x86_64 or ARM64. Keep the evaluation framework count intentionally low. Use urlInspect AIturn8search2 for agentic, multimodal, and tool-using evaluations; its docs highlight 200+ prebuilt evals, reusable components, MCP-capable tooling, and support for arbitrary external agents. Your judge layer should not be a single “magic model judge.” It should have three lanes. The first lane should be deterministic or executable scoring whenever ground truth exists. The second should be a pairwise judge for open-ended quality comparisons. The third should be a rubric judge that scores factuality, evidence use, locale appropriateness, OCR fidelity, and numeric consistency separately. That structure fits the state of the field: MT-Bench and Chatbot Arena showed that strong LLM judges can approximate human preference judgments at over 80% agreement, but the original paper also documented position, verbosity, and self-enhancement bias, while later survey work frames reliability and standardization as the central unresolved problems. citeturn34view0turn24view0

You also need a **judge-of-the-judge** layer. JudgeBench was created because judge reliability itself was being under-scrutinized, and its results show a genuinely difficult stress test: on JudgeBench, the strongest evaluated judge reached only 64% accuracy. Separate work on alignment-task judging recommends measuring not just headline accuracy, but also position bias and length bias explicitly. In practice, every judge you deploy should be tested on order-swapped answer pairs, length-controlled variants, and adversarially similar responses before you trust it in production. citeturn24view1turn24view2

The most important guardrail for your use cases is grounding. Recent work argues that judges often fail in exactly the domains where the judge model itself cannot solve the underlying task, and that human-written references improve agreement and reduce self-preference bias. For you, that means finance, OCR, and memory tasks should never be judged only by free-form preference. Carry gold references, evidence spans, or executable checks wherever possible, and reserve open-ended judging for the parts that are truly subjective. citeturn24view3

## The memory and context architecture

The current research picture is actually useful here. A recent survey frames agent memory as a write–manage–read loop and groups existing systems into context-resident compression, retrieval-augmented stores, reflective memory, hierarchical virtual context, and policy-learned management. That is the right design lens for your quarter: not “invent a new memory paper,” but “choose a reliable hierarchy and instrument it well.” citeturn26view0

My recommendation is a four-part memory plane. First, thread-scoped checkpoints for working state and resumability. Second, a long-term memory store keyed by user, project, and task. Third, an artifact layer for PDFs, OCR outputs, images, and tables. Fourth, an evaluation trace layer that records prompts, retrieved context, tool calls, and scores. The official persistence docs show checkpointing at each graph step for resumability and fault tolerance, while the long-term-memory docs define cross-session memory as JSON documents under namespaces and keys. Even if you do not adopt those libraries wholesale, those boundaries are exactly the right ones to preserve. citeturn26view2turn26view3

For storage, start simple: Postgres plus urlpgvectorturn5search2. The official pgvector docs give you exact nearest-neighbor search first and HNSW or IVFFlat approximate indexing later, which is a very good fit for a one-machine research lab that wants clean replay and SQL-native metadata. Use urlRedis vector searchturn5search3 only if you later need a lower-latency online serving tier with more aggressive filtering and retrieval performance requirements. citeturn27view0turn27view1

For context management, externalize everything that matters. A run should be reproducible from a model manifest, prompt version, checkpoint ID, memory namespace, artifact references, and tool trace, not from hidden state jammed into a giant prompt template. Standardize tools and context exchange around urlMCPturn5search1, and borrow the online/offline split from LightMem: fast online retrieval and writing during sessions, followed by slower consolidation, summarization, and contradiction handling offline on a daily or nightly schedule. That design is much more likely to transfer cleanly between local DGX execution and later cloud execution. citeturn26view4turn26view1

Build security into memory from day one. The current memory-security survey treats persistent memory as an independent attack surface, with write-path poisoning, retrieval corruption, control-flow hijacking, cross-agent propagation, rollback, and forget/delete semantics as separate governance problems. Its practical implication for your architecture is straightforward: validate writes, track provenance, scope retrieval by principal and project, preserve rollback points, and do not assume retrieval-time filtering alone is enough. citeturn29view0

## The quarterly roadmap

The quarter should end with one reproducible local evaluation lab, one calibrated judge service, one durable memory substrate, and one serious pilot that exercises all three. Anything that does not clearly move one of those four outcomes should be treated as backlog, not current work. citeturn17view0turn17view1turn26view0

**Foundation month.** Stand up the platform and standardize interfaces. Choose one blessed local runtime on the DGX box, ideally the official container path with NIM or TensorRT-LLM, and one challenger runtime for experimentation through Dynamo with vLLM or SGLang. Bring up Postgres plus pgvector, define a model manifest schema, and wire the first evaluation loop with lm-evaluation-harness for deterministic tasks and Inspect AI for multimodal and agentic tasks. By the end of this month, every model you test should be invocable through the same endpoint shape, every run should log prompts, outputs, timings, and artifacts, and you should have a curated gold set of roughly 250–400 examples split across general reasoning, Japanese/SEA language tasks, OCR/document tasks, and finance. citeturn7view0turn7view2turn9view0turn9view1turn27view0

**Judges and memory month.** Build the scoring layer and the memory kernel. Implement three judge modes: deterministic/executable, pairwise, and rubric. Add answer-order randomization, judge swap tests, and monthly human calibration. In parallel, implement thread checkpoints, long-term namespaces, artifact storage, and offline consolidation, with provenance attached to every memory write. This is also the month to add security controls such as write filters, rollback, and scoped retrieval, because doing that later is much harder than designing for it now. citeturn24view1turn24view2turn24view3turn26view2turn26view3turn29view0

**Deployment month.** Productionize the lab and pick one primary pilot. The best pilot for your profile is a multilingual document analyst that combines Japanese and SEA OCR, grounded document QA, and financial reasoning, because that single application exercises localization, VLM/OCR, evidence-grounded judging, and memory/context transfer all at once. Add nightly or weekly regression runs, a leaderboard view, Singapore-pinned storage policy, and one replay test that proves the same run can resume from stored state rather than from a handcrafted prompt.
